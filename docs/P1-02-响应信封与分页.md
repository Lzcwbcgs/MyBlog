## 2.3 完整代码

新建 `internal/handle/base.go`：

```go
package handle

import (
	g "gin-blog/internal/global"
	"log/slog"
	"net/http"

	"github.com/gin-gonic/gin"
	"github.com/redis/go-redis/v9"
	"gorm.io/gorm"
)

/*
响应设计方案：不使用 HTTP 码来表示业务状态, 采用业务状态码的方式
- 只要能到达后端的请求, HTTP 状态码都为 200
- 业务状态码为 0 表示成功, 其他都表示失败
- 当后端发生 panic 并且被 gin 中间件捕获时, 才会返回 HTTP 500 状态码
*/

// 响应结构体
type Response[T any] struct {
	Code    int    `json:"code"`    // 业务状态码
	Message string `json:"message"` // 响应消息
	Data    T      `json:"data"`    // 响应数据
}

// HTTP 码 + 业务码 + 消息 + 数据
func ReturnHttpResponse(c *gin.Context, httpCode, code int, msg string, data any) {
	c.JSON(httpCode, Response[any]{
		Code:    code,
		Message: msg,
		Data:    data,
	})
}

// 业务码 + 数据
func ReturnResponse(c *gin.Context, r g.Result, data any) {
	ReturnHttpResponse(c, http.StatusOK, r.Code(), r.Msg(), data)
}

// 成功业务码 + 数据
func ReturnSuccess(c *gin.Context, data any) {
	ReturnResponse(c, g.OkResult, data)
}

// 所有可预料的错误 = 业务错误 + 系统错误, 在业务层面处理, 返回 HTTP 200 状态码
// 对于不可预料的错误, 会触发 panic, 由 gin 中间件捕获, 并返回 HTTP 500 状态码
// err 是业务错误, data 是错误数据 (可以是 error 或 string)
func ReturnError(c *gin.Context, r g.Result, data any) {
	slog.Info("[Func-ReturnError] " + r.Msg())

	var val string = r.Msg()

	if data != nil {
		switch v := data.(type) {
		case error:
			val = v.Error()
		case string:
			val = v
		}
		slog.Error(val) // 错误日志
	}

	c.AbortWithStatusJSON(
		http.StatusOK,
		Response[any]{
			Code:    r.Code(),
			Message: r.Msg(),
			Data:    val,
		},
	)
}

// 分页获取数据
type PageQuery struct {
	Page int `form:"page_num"` // 当前页数（从1开始）
	// 每页条数; 限制成正数, 避免请求参数传进 model.PageSizeAll 变成全表查询
	Size    int    `form:"page_size" binding:"omitempty,min=1"`
	Keyword string `form:"keyword"` // 搜索关键字
}

// 分页响应数据
type PageResult[T any] struct {
	Page  int   `json:"page_num"`  // 当前页数
	Size  int   `json:"page_size"` // 每页条数
	Total int64 `json:"total"`     // 总条数
	List  []T   `json:"page_data"` // 分页数据
}

// 获取 *gorm.DB
func GetDB(c *gin.Context) *gorm.DB {
	return c.MustGet(g.CTX_DB).(*gorm.DB)
}

// 获取 *redis.Client
func GetRDB(c *gin.Context) *redis.Client {
	return c.MustGet(g.CTX_RDB).(*redis.Client)
}
```

装依赖：

```bash
go get gorm.io/gorm@v1.31.2
go get github.com/redis/go-redis/v9@v9.22.0
go mod tidy
```

## 2.4 逐段讲解

### ① 文件顶部那段注释 —— 整个项目的接口哲学

```go
/*
响应设计方案：不使用 HTTP 码来表示业务状态, 采用业务状态码的方式
- 只要能到达后端的请求, HTTP 状态码都为 200
- 业务状态码为 0 表示成功, 其他都表示失败
- 当后端发生 panic 并且被 gin 中间件捕获时, 才会返回 HTTP 500 状态码
*/
```

**这三条要理解透，因为它决定了前后端怎么协作。**

**「只要能到达后端的请求，HTTP 状态码都为 200」**

包括这些情况：

| 场景 | HTTP 码 | 业务码 |
|---|---|---|
| 登录成功 | 200 | 0 |
| 密码错误 | **200** | 1004 |
| 权限不足 | **200** | 1206 |
| 参数格式错误 | **200** | 9001 |
| 代码 panic（空指针等） | **500** | 500 |

**为什么这么设计？**

支持者说：业务错误是「正常业务流的一部分」，不是「请求失败」。密码错了、权限不够，都是预期内的结果，用 200 返回更合理。而且前端只需要判断一个地方。

反对者说：这丢掉了 HTTP 的语义。CDN、网关、APM 监控、浏览器 DevTools 都是按 HTTP 状态码工作的 —— 它们看到满屏 200，无法区分「一切正常」和「500 个权限错误」。

**这是个真实的取舍，不是对错问题。** 对这个小项目来说，「前端只判断一个地方」的收益更大。但如果接入 APM 或做灰度发布，这个设计会开始碍事。

**最后一条特别值得注意**：只有 **panic** 才返回 500。也就是说，「500 在这个项目里 = 真的有 bug」，而不是「某个业务失败了」。这让 500 变得非常可检索 —— 生产环境看到 500 就知道要查日志了。

### ② `Response[T]` —— Go 泛型在这里省了什么

```go
type Response[T any] struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    T      `json:"data"`
}
```

**没有泛型的话，你得这么写：**

```go
// 方案 A：Data 用 any
type Response struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data"`
}

// 方案 B：每种数据类型写一个
type ArticleResponse struct {
	Code    int             `json:"code"`
	Message string          `json:"message"`
	Data    []model.Article `json:"data"`
}
type UserResponse struct { ... }   // 再来一遍
type CommentResponse struct { ... } // 再来一遍
```

**方案 A 的问题**：`Data any` 在文档和类型上完全是「未知」，Swagger 生成出来 `data` 是空对象，IDE 也没有提示。

**方案 B 的问题**：60 个接口要写 60 个结构体，而且每个改动要改 60 处。

**泛型的解法**：`Response[T]` 是一个「模具」，`T` 在**使用的时候**才确定。

```go
// 写 handler 时
ReturnSuccess(c, article)        // 实际是 Response[any]{Data: article}

// Swagger 注释里（P9）
// @Success 0 {object} Response[LoginVO]
```

Swag 能解析 `Response[LoginVO]` 并生成出完整的嵌套 schema：

```json
{
  "code": 0,
  "message": "string",
  "data": { "id": 0, "username": "string" }
}
```

**这就是泛型在 Go 里最典型的用途之一**：给「外壳固定、内容可变」的结构做参数化。`Response`、`PageResult` 都是这个形状。

### ③ `ReturnError` 里的三件小事

**第一件：`slog.Info` 和 `slog.Error` 分开**

```go
func ReturnError(c *gin.Context, r g.Result, data any) {
	slog.Info("[Func-ReturnError] " + r.Msg())   // ← Info 级别
	...
	if data != nil {
		...
		slog.Error(val)                            // ← Error 级别
	}
	...
}
```

注意区别：**业务错误码本身只记 Info**，只有**带了 data（也就是真正的技术错误）才记 Error**。

为什么？因为「密码错误」「权限不足」这类业务错误**每天都在大量发生**，如果都记 Error，日志会被淹没，真正的技术错误就找不出来了。

这对应到 P0 里配的日志级别：

```yaml
Log:
  Level: "debug"
```

生产环境会设成 `error`，那时：

- `slog.Info("[Func-ReturnError] 权限不足")` → **被过滤掉，不输出**
- `slog.Error("db error: ...")` → **输出**

**这是个很实用的日志策略**：按级别控制「噪音」和「信号」的比例。

**第二件：类型断言的选择 —— `switch v := data.(type)`**

```go
if data != nil {
	switch v := data.(type) {
	case error:
		val = v.Error()
	case string:
		val = v
	}
	slog.Error(val)
}
```

参数 `data` 的类型是 `any`（可以是任何东西）。用 **type switch** 判断它实际是什么：

- 如果是 `error` 类型 → 取 `.Error()` 字符串
- 如果是 `string` → 直接用
- 都不是 → `val` 保持默认值 `r.Msg()`

**为什么不是简单的 `if`？** 因为要对不同类型做不同处理，`switch type` 是最清晰的写法。

**为什么要兼容这两种类型？** 因为调用方的习惯不同：

```go
ReturnError(c, g.ErrDbOp, err)                  // 传 error 对象
ReturnError(c, g.ErrTokenNotExist, "请重新登录") // 传字符串
```

两种都常见，所以两种都支持。

**第三件：`c.AbortWithStatusJSON` 而不是 `c.JSON`**

这个差异**非常重要**：

```go
c.JSON(...)                  // 写响应，然后【继续】执行后续 handler
c.AbortWithStatusJSON(...)   // 写响应，然后【中止】后续 handler
```

**为什么必须用 Abort？**

因为 `ReturnError` **会被中间件调用**：

```go
// middleware/auth.go（P3 要写的）
if authorization == "" {
	handle.ReturnError(c, g.ErrTokenNotExist, nil)
	return          // ← 这里的 return 只退出中间件函数
}
```

gin 的中间件是这样的结构：

```go
func SomeMiddleware() gin.HandlerFunc {
	return func(c *gin.Context) {
		// 前置逻辑
		c.Next()          // ← 这里才执行后续的中间件和 handler
		// 后置逻辑
	}
}
```

如果中间件里用 `c.JSON` 写完错误响应后就 `return`，**gin 仍然会继续执行后面的 handler** —— 因为 handler 链是 gin 内部维护的，你的 `return` 只退出了当前函数。

结果是：**响应被写两次**。第二次写的时候会报：

```
http: superfluous response.WriteHeader call
```

响应体也会变成两个 JSON 拼在一起。

`c.AbortWithStatusJSON` 会在写完响应后**把 gin 的 handler 索引置到末尾**，后续 handler 全部跳过。

**规则总结：**

| 位置 | 用什么 |
|---|---|
| 中间件里返回错误 | **必须** `c.AbortWithStatusJSON` |
| handler 里返回错误 | `Abort` 也无害（而且更安全，万一是被别人调用的辅助函数） |

原版统一用 `AbortWithStatusJSON`，这是更保守也更正确的选择。

> 顺带一提：`ReturnHttpResponse` 用的是 `c.JSON`（不 Abort），因为它是「写响应」的底层函数，不负责决定要不要中止流程。这是个合理的分层 —— **底层函数只做事，不做决定**。

### ④ `PageQuery` —— 请求参数的解析

```go
type PageQuery struct {
	Page    int    `form:"page_num"`                            // 当前页数（从1开始）
	Size    int    `form:"page_size" binding:"omitempty,min=1"` // 每页条数
	Keyword string `form:"keyword"`                             // 搜索关键字
}
```

**`form` tag 是干嘛的？**

gin 的 `c.ShouldBindQuery(&pageQuery)` 会按这个 tag 去 URL 查询串里找参数：

```
GET /api/article/list?page_num=1&page_size=10&keyword=golang
```

`form:"page_num"` 表示「把 URL 里的 `page_num` 填进 `Page` 字段」。

**为什么用 `form` 而不是 `json`？**

因为这是 **GET 请求** —— 参数在 URL 里，不在请求体里。gin 有不同的绑定方法：

| 方法 | 读哪里 | 对应 tag |
|---|---|---|
| `ShouldBindQuery` | URL 查询串 | `form` |
| `ShouldBindJSON` | 请求体 JSON | `json` |
| `ShouldBind` | 自动判断（按 Content-Type） | 看情况 |

**`binding:"omitempty,min=1"` 是干什么的？**

这是**参数校验**。拆开看：

- `omitempty` —— 如果不传（零值），跳过校验
- `min=1` —— 如果传了，必须 ≥ 1

**为什么需要它？** 看注释：

```go
// 每页条数; 限制成正数, 避免请求参数传进 model.PageSizeAll 变成全表查询
```

`PageSizeAll` 是 P2 会引入的一个常量，值是 `-1`，意思是「不分页，返回全部」。它**只给服务端代码用**。

如果请求参数能传 `-1` 进来：

```
GET /api/article/list?page_size=-1
```

就会走 `PageSizeAll` 分支，**一次把全表查出来**。文章表有几万行的话，这一条请求就能把数据库打死。

`min=1` 就是堵这个口子 —— 请求参数进来时 `page_size` 必须 ≥ 1，服务端代码才能在内部用 `-1`。

> **这是个典型的「信任边界」问题**：`PageSizeAll` 这个值在服务端是合法参数，在客户端是攻击载荷。同一个数字，来源不同，含义完全不同。
>
> 正确的做法是在**入口处**校验（binding tag），而不是在每个用到它的地方防御。

**注意 `Page` 字段没有校验**，因为 `model.Paginate`（P2）里会自己处理：

```go
if page <= 0 {
	page = 1
}
```

参数非法就退化成第 1 页，不用报错 —— 这个体验更好。

### ⑤ `PageResult[T]` —— 响应的分页形状

```go
type PageResult[T any] struct {
	Page  int   `json:"page_num"`  // 当前页数
	Size  int   `json:"page_size"` // 每页条数
	Total int64 `json:"total"`     // 总条数
	List  []T   `json:"page_data"` // 分页数据
}
```

**注意这里的命名差异，前端会踩：**

| 方向 | 字段名 |
|---|---|
| **请求** | `page_num` / `page_size` / `keyword` |
| **响应** | `page_num` / `page_size` / `total` / **`page_data`** |

列表数据叫 **`page_data`**，不叫 `list` 也不叫 `data`。

前端调用时是这样：

```js
const { data } = await api.getArticles({ page_num: 1, page_size: 8 })
// data.page_data  ← 列表在这里
// data.total      ← 总数在这里
```

**为什么要专门包一层 `PageResult`，而不直接返回 `[]T`？**

因为前端要算总页数：

```js
const pageCount = Math.ceil(total / pageSize)
```

没有 `total` 就没法渲染分页器。这是**服务端必须告诉客户端的信息** —— 客户端自己数不出来（它只拿到了当页的数据）。

**`Total` 为什么是 `int64` 而不是 `int`？**

因为数据库的 `COUNT(*)` 返回的是 `int64`。用 `int` 的话每处都要转换。而且理论上 `int` 在 32 位平台上是 32 位，表大了会溢出（虽然实际上不会）。

### ⑥ `GetDB` / `GetRDB` —— 依赖注入的消费端

```go
func GetDB(c *gin.Context) *gorm.DB {
	return c.MustGet(g.CTX_DB).(*gorm.DB)
}

func GetRDB(c *gin.Context) *redis.Client {
	return c.MustGet(g.CTX_RDB).(*redis.Client)
}
```

**这两行代码，是整个后端「依赖注入」设计的消费端。**

拆解一下发生了什么：

```go
c.MustGet(g.CTX_DB)     // 1. 从 gin.Context 里取出 key 为 "_db_field" 的值，类型是 any
    .(*gorm.DB)         // 2. 类型断言：我确信它是 *gorm.DB
```

**`MustGet` vs `Get`：**

```go
c.Get(key)      // (value any, exists bool) —— 不存在时返回 nil, false
c.MustGet(key)  // value any —— 不存在时【panic】
```

原版用 `MustGet`。理由是：**DB 和 Redis 的注入是全局中间件做的**（本阶段第 3 节的 `WithGormDB` / `WithRedisDB`），只要服务正常启动，它们一定在 Context 里。

如果 `MustGet` panic 了，说明**中间件没注册或者顺序错了** —— 这是个**编程错误**，应该在开发期就炸掉，而不是让 handler 拿到 nil 再出更诡异的错。

**「什么时候该 panic」的判断标准**：这个失败是「运行时的正常可能」，还是「代码写错了」？

- 用户传了不存在的 id → 正常可能 → 返回业务错误
- Context 里没有 DB → 代码写错了 → panic 更好

**为什么叫「依赖注入」？**

传统的写法是全局变量：

```go
var DB *gorm.DB          // 包级全局
func GetArticle(c *gin.Context) {
	db := DB             // 直接用全局
}
```

问题：**测试时没法替换**。你想用一个内存 SQLite 测 handler，只能去改那个全局变量（而且并发测试会互相污染）。

gin Context 的方案是：

```go
// 启动时注入（middleware/base.go）
func WithGormDB(db *gorm.DB) gin.HandlerFunc {
	return func(ctx *gin.Context) {
		ctx.Set(g.CTX_DB, db)   // ← 塞进去
		ctx.Next()
	}
}

// 测试时注入测试库
r.Use(func(c *gin.Context) {
	c.Set(g.CTX_DB, testDB)    // ← 换个库，handler 代码一行不改
	c.Next()
})
```

**`*gorm.DB` 是按请求存的**，每个请求有自己的 context，互不干扰 —— 并发安全的测试就这么来的。

原版 `internal/handle/testenv_test.go` 就是这么做的，P9 你会看到。

## 2.6 本节留下的伏笔

- `ReturnError` 里的 `AbortWithStatusJSON` —— **第 3 节写中间件时你会真正体会到为什么要 Abort**。
- `PageQuery` 的 `min=1` 是在堵 `model.PageSizeAll` —— **P2 会看到那个 `-1` 从哪来**。
- `GetDB` / `GetRDB` 依赖 Context 里有值 —— **第 3 节的 `WithGormDB` / `WithRedisDB` 负责塞进去**。
- `slog` 现在还没被初始化 —— **第 4 节 `InitLogger` 才会配它**。在那之前 `slog` 用的是默认配置（输出到 stderr，Info 级别）。
